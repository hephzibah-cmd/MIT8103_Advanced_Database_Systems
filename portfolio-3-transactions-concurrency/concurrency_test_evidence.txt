EXPERIMENT 1: LOST UPDATE - READ COMMITTED vs REPEATABLE READ
========================================================================
Account a0000001-0000-4000-8000-000000000001 (Amina USD) starting balance: 14248.5000
Two concurrent sessions each withdraw 800.0000 via naive read-modify-write:
  SELECT current_balance ...;  -- application computes balance - amount
  UPDATE accounts SET current_balance = <computed value> ...;
A barrier guarantees both sessions READ before either WRITES.

--- 1a: READ COMMITTED ---
  [Thread-1] attempt 1: read balance 14248.5000
  [Thread-2] attempt 1: read balance 14248.5000
  [Thread-1] attempt 1: COMMIT, wrote balance 13448.5000
  [Thread-2] attempt 1: COMMIT, wrote balance 13448.5000
>> RESULT (READ COMMITTED): final balance = 13448.5000
   Correct (both withdrawals applied): 12648.5000
   [ANOMALY CONFIRMED] Lost update: one 800.0000 debit was overwritten;
   800.0000 was paid out but never deducted from the account.
   (touched accounts restored to their pre-experiment state)

--- 1b: REPEATABLE READ ---
  [Thread-1] attempt 1: read balance 14248.5000
  [Thread-2] attempt 1: read balance 14248.5000
  [Thread-2] attempt 1: COMMIT, wrote balance 13448.5000
  [Thread-1] attempt 1: SQLSTATE 40001 SerializationFailure ('could not serialize access due to concurrent update') -> ROLLBACK, retry
  [Thread-1] attempt 2: read balance 13448.5000
  [Thread-1] attempt 2: COMMIT, wrote balance 12648.5000
>> RESULT (REPEATABLE READ): final balance = 12648.5000
   Correct (both withdrawals applied): 12648.5000
   [PASS] No lost update: the stale writer was aborted with SQLSTATE 40001
   (first-updater-wins under snapshot isolation) and its retry re-read
   the committed balance.
   (touched accounts restored to their pre-experiment state)

EXPERIMENT 2: ATOMIC PESSIMISTIC GUARD (SOLVENCY-PRESERVING DECREMENT)
========================================================================
Account a0000001-0000-4000-8000-000000000001 balance 14248.5000, overdraft_limit 1000.00 -> spendable 15248.5000
Two concurrent sessions (READ COMMITTED) each try to withdraw 9000.0000;
one fits, two do not. Each runs a single guarded UPDATE:
  UPDATE accounts SET current_balance = current_balance - :amount
  WHERE account_id = :id AND (current_balance + overdraft_limit) >= :amount;
Each session holds its row lock ~0.3s before COMMIT so the other must wait.

  [Thread-2] SUCCESS: rowcount=1, new balance=5248.5000 (UPDATE waited 1 ms)
  [Thread-1] REJECTED: rowcount=0 - blocked 305 ms on the row lock, then re-evaluated the guard against the committed row

>> RESULT: Final balance = 5248.5000 (expected 5248.5000)
   [PASS] Exactly one debit applied; the second was rejected by the guard
   (READ COMMITTED re-checks the WHERE clause on the newest row version
   after the lock wait). No lost update, no overdraft breach.
   (touched accounts restored to their pre-experiment state)

EXPERIMENT 4: DEADLOCK - DETECTION (40P01) vs PREVENTION (LOCK ORDERING)
========================================================================
Bidirectional transfers between two accounts:
  Transfer A: Amina a0000001-0000-4000-8000-000000000001 -> Chidi a0000002-0000-4000-8000-000000000002  $100.00
  Transfer B: Chidi a0000002-0000-4000-8000-000000000002 -> Amina a0000001-0000-4000-8000-000000000001  $200.00
Each transfer locks both rows with SELECT ... FOR UPDATE, then debits/credits.
A barrier makes both sessions hold their FIRST lock before requesting the second.

--- 4a: UNORDERED (source first, then destination) ---
  [Thread-2] attempt 1: locked a0000002
  [Thread-1] attempt 1: locked a0000001
  [Thread-2] attempt 1: locked a0000001
  [Thread-1] attempt 1: SQLSTATE 40P01 DeadlockDetected - chosen as victim, ROLLBACK, retry
  [Thread-2] attempt 1: COMMIT transfer 200.0000 a0000002 -> a0000001, locks released
  [Thread-1] attempt 2: locked a0000001
  [Thread-1] attempt 2: locked a0000002
  [Thread-1] attempt 2: COMMIT transfer 100.0000 a0000001 -> a0000002, locks released
>> RESULT: deadlocks=1, Amina net change 100.0000 (expected +100.0000), combined balance 22748.5000 (expected 22748.5000)
   [PASS] PostgreSQL's wait-for-graph check (after deadlock_timeout) aborted
   one victim with 40P01; the survivor committed and the victim's retry
   succeeded. Detection resolves deadlocks, but costs ~1s and an abort.
   (touched accounts restored to their pre-experiment state)

--- 4b: CANONICAL ORDER (min id, then max id) ---
  [Thread-1] attempt 1: locked a0000001
  [Thread-1] attempt 1: locked a0000002
  [Thread-1] attempt 1: COMMIT transfer 100.0000 a0000001 -> a0000002, locks released
  [Thread-2] attempt 1: locked a0000001
  [Thread-2] attempt 1: locked a0000002
  [Thread-2] attempt 1: COMMIT transfer 200.0000 a0000002 -> a0000001, locks released
>> RESULT: deadlocks=0, Amina net change 100.0000 (expected +100.0000), combined balance 22748.5000 (expected 22748.5000)
   [PASS] Canonical ordering removed the circular wait: zero deadlocks,
   the second session simply queued behind the first.
   (touched accounts restored to their pre-experiment state)

EXPERIMENT 5: WRITE SKEW - REPEATABLE READ vs SERIALIZABLE (SSI)
========================================================================
Zainab (a0000005) and Kolawole (a0000006) are a guarantor pair under a
combined-collateral rule: balance_zainab + balance_kolawole >= 150000.0000
Starting combined balance: 157400.7500
Each session reads BOTH balances, checks the rule for a 6000.0000 withdrawal,
then debits ONLY its own account (disjoint write sets, so no row conflict).
One withdrawal is fine (151400.7500); both breach the rule (145400.7500).

--- 5a: REPEATABLE READ ---

  [Thread-2] attempt 1: read combined balance 157400.7500
  [Thread-2] attempt 1: COMMIT, debited 6000.0000 from a0000006
  [Thread-1] attempt 1: COMMIT, debited 6000.0000 from a0000005
>> RESULT (REPEATABLE READ): combined balance = 145400.7500 (rule >= 150000.0000)
   [ANOMALY CONFIRMED] Write skew: each snapshot saw a valid state, both
   committed, and the combined-collateral rule is now violated.
   (touched accounts restored to their pre-experiment state)

--- 5b: SERIALIZABLE ---

  [Thread-1] attempt 1: read combined balance 157400.7500
  [Thread-2] attempt 1: SQLSTATE 40001 SerializationFailure ('could not serialize access due to read/write dependencies among transactions') -> ROLLBACK, retry
  [Thread-1] attempt 1: COMMIT, debited 6000.0000 from a0000005

  [Thread-2] attempt 2: rule would be breached -> withdrawal declined
>> RESULT (SERIALIZABLE): combined balance = 151400.7500 (rule >= 150000.0000)
