# Portfolio 3: Transactions and Concurrency
**Course:** MIT 8103 Advanced Database Systems  
**Case Study:** ApexBank Digital (Next-Generation Digital Banking & Fintech Platform)  
**Database Engine:** PostgreSQL 16  
**Schema:** Portfolio 1 (`../portfolio-1-database-design/ddl_schema.sql`)

---

### Executive Summary

Portfolio 3 presents practical implementations, architectural explanations, and empirical simulation logs demonstrating ACID transaction processing, rollback mechanisms, isolation level guarantees, and concurrency control in **ApexBank Digital**. All experiments execute against the **live Portfolio 1 PostgreSQL schema** (tables, triggers, deferred constraints, `chk_account_solvency`, idempotency uniqueness, append-only ledger/journal) in a dedicated `apexbank_concurrency` database — Portfolio 1's `apexbank` database is never modified.

### Setup & Run

From the repository root:

```bash
# 1. Start PostgreSQL 16 (once)
docker compose up -d

# 2. Install Python dependencies (psycopg[binary]>=3.2)
pip install -r requirements.txt

# 3. Run Portfolio 3
python portfolio-3-transactions-concurrency/concurrency_runner.py
```

The runner connects via `P3_DATABASE_URL` (default: `postgresql://apexbank:apexbank_dev@localhost:5432/apexbank_concurrency`). Override with:

```powershell
$env:P3_DATABASE_URL="postgresql://apexbank:apexbank_dev@localhost:5432/apexbank_concurrency"
```

What the runner does:

1. Creates/reuses the `apexbank_concurrency` database (P1's `apexbank` database is untouched).
2. Loads Portfolio 1 DDL and seed data into the concurrency database.
3. Executes the five ACID transaction scripts from `transactions.sql` and verifies each outcome (balances, journals kept/discarded).
4. Asserts Portfolio 1 invariants (journal balance, `current_balance == latest balance_after`, solvency, append-only).
5. Runs six multithreaded concurrency experiments via `concurrency_simulation.py`.
6. Re-asserts the Portfolio 1 invariants and writes `concurrency_test_evidence.txt`.

Experiments 1-5 deliberately write `accounts.current_balance` directly (bypassing the P1 ledger posting path) so that each one isolates a single concurrency mechanism. Each experiment snapshots the rows it touches and restores them afterwards, so every experiment starts from the same known state and the post-run ledger reconciliation check is meaningful. A `threading.Barrier` forces the relevant interleaving, so the outcomes are deterministic (verified over repeated runs); only the thread that "wins" a race varies.

### Key Concurrency Experiments & Findings

1. **Lost Update - READ COMMITTED vs REPEATABLE READ:**
   - Two simultaneous $800 withdrawals via naive read-modify-write (`SELECT` balance, compute in the application, `UPDATE ... SET current_balance = <value>`). Under READ COMMITTED both commit and one debit is silently overwritten (final balance is only $800 lower) - **anomaly confirmed**. Under REPEATABLE READ PostgreSQL aborts the stale writer with SQLSTATE `40001` (*could not serialize access due to concurrent update*, first-updater-wins); the retry re-reads and both debits are applied.

2. **Pessimistic Atomic Invariant Enforcement:**
   - `UPDATE accounts SET current_balance = current_balance - :amount WHERE account_id = :id AND (current_balance + overdraft_limit) >= :amount`. Two concurrent $9,000 debits where only one fits: the second session blocks on the row lock, then READ COMMITTED re-evaluates the guard against the newly committed row and matches 0 rows. Exactly one debit applies.

3. **Optimistic Concurrency Control (OCC):**
   - Compare-And-Swap on the `accounts.version` column. Threads read `(balance, version)`, then `UPDATE ... SET version = version + 1 WHERE version = :read_version`. The loser gets `rowcount = 0`, re-reads and retries; both debits are applied and the version advances by 2. No lock is held between the read and the write.

4. **Deadlock - Detection vs Prevention:**
   - Bidirectional transfers between two accounts using `SELECT ... FOR UPDATE`. (4a) Locking source-then-destination produces a real circular wait; PostgreSQL's deadlock detector (after `deadlock_timeout` = 1s) aborts one victim with SQLSTATE `40P01`, which is retried. (4b) Locking in canonical order (`min(account_id)` first) removes the circular wait: the second session queues and both commit with zero deadlocks.

5. **Write Skew - REPEATABLE READ vs SERIALIZABLE:**
   - Two sessions each read the combined balance of a guarantor pair (rule: combined >= $150,000) and each debit $6,000 from a *different* account. Under REPEATABLE READ (snapshot isolation) both commit and the rule is violated - **anomaly confirmed**. Under SERIALIZABLE, PostgreSQL's SSI detects the read/write dependency cycle and aborts one session with SQLSTATE `40001`; its retry sees the other debit and declines.

6. **Idempotency Key Under Concurrency:**
   - Two sessions insert the same `idempotency_key` simultaneously: the second blocks on the unique index until the first commits, then raises `UniqueViolation` - exactly one payment row. Replaying an already-settled key also raises `UniqueViolation` and rolls back, preventing double debit.

### Relationship to Portfolio 1

- **Schema:** Portfolio 3 reuses `../portfolio-1-database-design/ddl_schema.sql` and `../portfolio-1-database-design/seed_data.sql` verbatim (loaded into `apexbank_concurrency`, not `apexbank`).
- **The `version` column:** A `version INTEGER NOT NULL DEFAULT 1` column was added to P1's `accounts` table (`ddl_schema.sql:93`) to give OCC a physical compare-and-swap target. This is purely additive — existing seed data and P1 verification are unaffected (re-verified with `verify_schema.py`).
- **Triggers exercised (by `transactions.sql` and the invariant checks):** `trg_ledger_apply_balance`, `trg_ledger_balanced`, `trg_journal_has_lines`, `trg_transaction_currency_guard`, `trg_*_append_only`, `chk_account_solvency`, `chk_account_holds`, `UNIQUE (idempotency_key)`.
